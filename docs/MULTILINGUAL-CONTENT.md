# Multilingual content contract

- Data: Russian is the existing source language; Kazakh (`kk`) and English (`en`) are translations. Reuse ContentDocument, ContentRevision and ContentAudit, with reserved internal IDs `i18n.<locale>.<baseId>`. These are variants of existing materials, not new tests. A translation stores a source snapshot and translated value. No existing records are rewritten or deleted.
- Processes: draft, publish and restore are independent per language, with revision comparison and atomic document/history/audit writes. No automatic write retries. Shared numbers, booleans, identifiers, links and structural fields cannot be translated. Missing translations and text whose source has changed fall back to Russian. Publication never changes shared navigator database projections.
- Policies: existing verified content-admin capabilities apply. Clients cannot create arbitrary documents or languages. Public reads exclude drafts and internal storage envelopes.
- Queries and frontend operations: locale travels explicitly through feature GraphQL operations and the editor BFF. The editor keeps language selection separate from the visitor language cookie. Visitors select a language and reload server-rendered content. Existing bilingual landing text is preserved. Language fallback does not claim an automatic translation.
- Realtime: none. Local previews update immediately; published content is fetched on the next request.
- Backups: the existing export includes translation variants and their histories. Import recognizes only variants of existing base documents and restores drafts atomically.
- Acceptance: three locales; invalid locale and unauthorized edits rejected; independent drafts/publications/history; unchanged source preserved; changed source falls back; shared fields protected; stale revision rejected; translated tests accepted as valid attempt snapshots; backup round-trip; recorded editor and public language-switch checks on the isolated VM.
